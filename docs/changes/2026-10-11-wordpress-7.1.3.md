# WordPress 7.1.3 fallback selection

- Date: 2026-10-11
- Owner: Codex
- Status: complete
- Disposition: kept
- Related version: unreleased
- Related commit/issue: Working-tree update; supersedes only the WordPress fallback selection described in [the current baseline](2026-08-28-current-baseline.md).

## Context

The user requested a WordPress version update. The source-controlled selector fallback offered WordPress 7.1 and older branches, while the official WordPress version API reported 7.1.3 as the current stable upgrade. Successful live API refreshes already supplied exact releases, but an API failure left the current patch release absent from the fallback selector.

## Hypothesis and success criteria

WordPress 7.1.3 should be selectable before the API refresh or when it fails. Preserve the 7.1 choice and every older branch. Keep fallback `latest` unresolved and use the official API to resolve it at launch. Saved recipes and OPFS site identity must retain their existing contracts.

## Options considered

- Leave unchanged: successful API refreshes already include 7.1.3, but the fallback misses the requested version.
- Replace 7.1 with 7.1.3: removes an existing selectable branch unnecessarily.
- Add 7.1.3 beside 7.1: the smallest change that updates the fallback and preserves existing choices. Implemented.
- Extend the scheduled sync to patch releases: broader automation and release-metadata behavior changes are outside this update.

## Implementation or prototype

Added `{ value: '7.1.3', label: 'WordPress 7.1.3' }` immediately after `latest` in [the WordPress version fallback](../../src/lib/wordpress-versions.js). The `latest` entry, runtime version fetch, saved-version preservation, recipe defaults, and OPFS identity logic are unchanged. The existing release sync still tracks major/minor branches; this exact patch fallback is a manual addition.

```sh
node --input-type=module <<'NODE'
import assert from 'node:assert/strict'
import {
  WORDPRESS_VERSION_FALLBACK_OPTIONS,
  fetchWordPressVersionOptions,
  getLatestStableWordPressVersion,
} from './src/lib/wordpress-versions.js'
assert.deepEqual(WORDPRESS_VERSION_FALLBACK_OPTIONS[1], { value: '7.1.3', label: 'WordPress 7.1.3' })
assert.deepEqual(WORDPRESS_VERSION_FALLBACK_OPTIONS.slice(2).map(({ value }) => value), ['7.1', '7.0', '6.9', '6.8', '6.7', '6.6', '6.5', '6.4', '6.3'])
assert.equal(WORDPRESS_VERSION_FALLBACK_OPTIONS[0].resolvedVersion, '')
assert.equal(getLatestStableWordPressVersion(WORDPRESS_VERSION_FALLBACK_OPTIONS), '')
const options = await fetchWordPressVersionOptions({ signal: AbortSignal.timeout(30000) })
assert.equal(getLatestStableWordPressVersion(options), '7.1.3')
assert.ok(options.some(({ value }) => value === '7.1.3'))
console.log('Fallback assertions passed; official API latest=7.1.3.')
NODE
```

Source inspection confirms only the fallback list changed in application code. Browser launch, API-failure UI behavior, and OPFS resume were not executed for this update.

## Result

WordPress 7.1.3 is included in the fallback list and every existing branch remains selectable. The executed module check confirms fallback `latest` remains unresolved and the official API resolves live `latest` to 7.1.3. All 63 existing tests and the production build passed. The build emitted browser-externalization and large-chunk warnings.

## Disposition and rationale

Kept. The single fallback entry supplies the requested patch release without changing live resolution, recipes, or persistence. Automated checks passed; browser runtime compatibility is not claimed.
